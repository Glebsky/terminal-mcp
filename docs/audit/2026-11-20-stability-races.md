# Аудит: стабильность, идемпотентность, гонки · 2026-11-20

**Вердикт.** Жизненный цикл сервера в десктопе (start / stop / выход) сделан аккуратно и повторные нажатия переживает. Ломаются края: параллельные правки одного файла молча теряются, рабочая папка одна на всех клиентов, занятый порт выдаётся за «работает», таймаут команды не ограничивает вызов, headless-браузер не переживает второго вызова, Cloudflare quick tunnel умирает после первого переподключения. Пункты 1–4 и 6 воспроизведены на изолированном стенде (`docs/audit/race-audit.cjs`), пункт 5 и часть средних найдены по коду.

**Чинить первыми:** блокировка и атомарная запись в файловых инструментах (1), изоляция cwd и удаление тихого фолбэка в FILES_ROOT (2), ошибка `listen` как состояние error (3), гарантированный возврат `terminal_execute` (4). 5 и 6 дешёвые и идут следом.

## 1. Параллельные правки файла теряются

`src/tools/filesystem.ts:200, 228`: `file_replace` делает read → modify → write без блокировки, а запись (`:178`, `:228`) идёт как truncate + write поверх живого файла.

Стенд B: 20 параллельных `file_replace` по разным строкам одного файла. Два прогона: 18 и 19 ответов `replacements: 1`, в файле оба раза осталось 2 правки (16 и 17 потеряны молча). Оставшиеся вызовы получили «Target content was not found», хотя строка в файле была: они прочитали файл в момент перезаписи. В живой работе то же самое: 20 ноября 7 параллельных правок `desktop/src/main/index.ts` через этот сервер вернули успех, две из них пропали.

Агенты часто шлют правки пачкой, так что это самая дорогая находка: успех без результата.

**Фикс.** Per-path async mutex (`Map<realpath, Promise>`, на Windows ключ в нижнем регистре) для write / replace / move / delete; для move брать оба пути в отсортированном порядке. Перезапись через temp-файл в той же папке + `rename` с несколькими ретраями на EPERM/EBUSY (антивирус и индексатор на Windows). Для ретраев: если target не найден, а replacement уже стоит ровно один раз, возвращать `already_applied: true` вместо ошибки.

Рядом: `file_replace` читает и пишет только UTF-8 (`:200`, `:228`), поэтому файл в cp1251 будет молча испорчен целиком (все не-ASCII байты станут U+FFFD). Нужна проверка `Buffer.from(text, "utf8").equals(raw)` и отказ, если байты не совпали.

## 2. Одна рабочая папка на всех и тихий фолбэк в FILES_ROOT

`filesystem.ts:14`: `currentWorkingDir` один на процесс; `command.ts:151`: голый `cd` в `terminal_execute` меняет его для всех; `/mcp` работает без сессий и создаёт новый McpServer на каждый запрос (`server.ts:88`), так что привязать cwd к клиенту сейчас не к чему. `filesystem.ts:120`: если относительного пути нет в cwd, но есть в FILES_ROOT, берётся FILES_ROOT.

Стенд C: агент 1 ставит cwd = projA, агент 2 ставит projB, относительная запись агента 1 попадает в `projB\agent1-note.txt`.
Стенд I: cwd = projA, `file_write("notes/todo.md")` записан в `FILES_ROOT\notes\todo.md`, корневой файл перезаписан, в projA ничего. Один и тот же вызов пишет в разные места в зависимости от того, что уже лежит на диске.

При двух подключённых агентах (Notion, ClickUp, Cursor) `file_delete` или `file_write` с относительным путём бьёт по чужому проекту.

**Фикс.** Минимум: убрать фолбэк для изменяющих операций (write / replace / move / delete / mkdir) и не менять общий cwd из `terminal_execute`. Лучше: cwd на сессию (stateful Streamable HTTP с `Mcp-Session-Id`; у SSE сессии уже есть) и явный параметр `cwd` у файловых инструментов.

## 3. Занятый порт выдаётся за «работает»

`src/index.ts:8–15`: Express 5.3 вызывает колбэк `listen` и при ошибке (`server.once('error', done)` в `node_modules/express/lib/application.js`), а наш колбэк аргумент игнорирует, шлёт `server:ready` и запускает туннель.

Стенд A: порт занят другой программой → `server:ready` пришёл, процесс жив, `/health` на этом порту не отвечает, EADDRINUSE нигде не залогирован. В десктопе это зелёный «работает» и публичный туннель, смотрящий в чужой процесс (например, в старый Notion Terminal MCP, если он на том же порту).

**Фикс.** В колбэке `(err) => { if (err) { console.error(...); process.send?.({ type: "server:error", code: err.code }); process.exit(1); } ... }`; в `ServerManager` состояние error с текстом «Порт N занят».

## 4. Таймаут terminal_execute не ограничивает вызов

`command.ts:128–135`: результат отдаётся только по `close`, а `close` ждёт, пока закроются все копии stdout/stderr. Фоновый процесс, унаследовавший пайп (`start /b`, dev-серверы), держит вызов, а `taskkill /T` его не находит, когда промежуточный родитель уже вышел.

Стенд D: `cmd`: `start /b ping -n 9 127.0.0.1 >nul`, `timeout_ms: 1500` → вызов вернулся через 8198 мс с `timedOut: true`. С `ping -t` или dev-сервером через `start /b` вызов висит бесконечно.

Плюс обработчики инструментов не берут `extra.signal` (`tools/index.ts:65`): когда клиент отвалился, команда работает дальше, а клиент на ретрае запускает её второй раз.

**Фикс.** Резолвить по `exit` + 300–500 мс на дочитку вывода, потом `stdout/stderr.destroy()`; жёсткий потолок `timeout + 2 с` независимо от `close`; `signal` → `killProcessTree`; в результате флаг, что фоновые процессы могли остаться.

## 5. Headless-браузер живёт ровно один вызов (по коду)

`browser.ts:288`: `ensurePage(headless = false)`, а `navigate / evaluate / click / type / getContent / screenshot` (`:388`–`:539`) вызывают его без аргументов. `:235` видит несовпадение режима, закрывает headless-браузер и запускает видимый с пустой вкладкой. После `browser_open({ headless: true })` любой следующий browser_* теряет страницу.

Ещё `ensureBrowser` без single-flight (`:260`): два параллельных первых вызова запускают два Chrome, ссылка на первый теряется до остановки сервера. Браузер один на всех клиентов, как и cwd.

**Фикс.** `ensurePage(headless = this.isHeadless)`; общий `launching?: Promise<Browser>` для launch и attach. Не запускал, чтобы не открывать окна на экране; код однозначный.

## 6. Cloudflare quick tunnel умирает после первого переподключения

`tunnel/cli.ts:97` считает `Unregistered tunnel connection` потерей связи, а восстановлением для quick-режима считает только повтор строки с URL (`:85`), которую cloudflared печатает один раз. `status.ts:15` на время `starting` убирает хост туннеля из ALLOWED_HOSTS.

Стенд E (фейковый cloudflared): `/health` через хост туннеля 200 → одно переподключение соединения → 421 сразу, хотя соединение вернулось через секунду → через 40 с состояние `error`, процесс туннеля убит, автоперезапуска нет. Переподключения cloudflared к edge случаются регулярно, так что quick tunnel долго не живёт. Tuna и localtunnel идут через тот же watchdog, их вывод не симулировал.

**Фикс.** `Registered tunnel connection` считать восстановлением и для quick (с последним URL); не убирать хост, пока URL не сменился; после выхода CLI перезапускать его с backoff, как у ngrok.

## Средние

- **`file_read` режет UTF-8** (`filesystem.ts:157`). Стенд G: «привет» кусками по 3 байта → `"п�"` + `"�и"`. Агент, который собирает большой файл по кускам и пишет обратно, портит кириллицу. В живой работе чтение `ru.ts` с `length: 2000` кончилось на «Запустит�». Фикс: резать по границе символа и отдавать `next_offset`.
- **Ретраи не идемпотентны.** `enableJsonResponse: true` (`server.ts:89`): ответ только в конце, без прогресса, и длинный вызов через туннель упирается в таймаут прокси (у Cloudflare около 100 с). Клиент повторяет, первый запуск продолжается. Неидемпотентны: `terminal_execute`, `file_write` с append, `file_replace` (если replacement содержит target), `file_move` (повтор после успеха = ENOENT), `browser_click` / `browser_type` / `browser_new_tab`. Фикс: `signal` (п. 4), опциональный `idempotency_key` с коротким кэшем результатов, `already_applied` в replace.
- **ngrok: свой reconnect поверх встроенного (гипотеза).** SDK 1.7 сам переподключается (`onStatusChange`: `closed` → `connected`), а `tunnel/ngrok.ts` через 2 с после `closed` закрывает listener и открывает новую сессию (`force_new_session: true`). Если сеть лежит дольше 2 с, приложение сносит сессию, которая уже восстанавливается. Что наблюдалось через рабочий ngrok во время проверки: два вызова упали с ERR_NGROK_3004 (около 13:13 и 13:19; второй точно не дошёл до сервера, файл не создался), с 13:21 до 13:24 туннель отдавал 404 при живом процессе сервера, затем примерно с 13:28 снова 404, а в 13:31:49 процесс сервера был запущен заново внутри того же приложения (новый PID, Electron тот же с 9:38). Контрольный вызов после 80 с тишины прошёл, так что простой keep-alive не виноват. Причину покажут строки `[Ngrok]` и `MCP Server stopped (exit code: …)` во вкладке «Логи» за 13:13–13:32.
- **Поиск может повесить весь сервер** (по коду). Защита от ReDoS (`filesystem.ts:311`) ловит только вложенные квантификаторы; `(a|aa)*c` проходит и на строке из `a` экспоненциален. Regex крутится в главном потоке (`:386`), и встают все клиенты, монитор и IPC-остановка. Фикс: worker с таймаутом или RE2.
- **Лог в десктопе режет строки** (по коду). `desktop/src/main/server-manager.ts:341–347` парсит каждый chunk как набор целых строк, без буфера и StringDecoder: под нагрузкой `[AUDIT]`-строки рвутся надвое, кириллица на границе превращается в «�». Фикс: `readline` по stdout/stderr.

## Мелкие

- `server-manager.ts:353, 362`: обработчики `close` / `error` старого процесса обнуляют `this.process` без проверки, что это тот же процесс. Опоздавший `close` после быстрого Stop → Start потеряет ссылку на новый сервер. Фикс: `if (this.process === proc)`.
- `filesystem.ts:258`: рекурсивный `file_list` падает целиком на одной недоступной подпапке (в `searchFiles` try/catch есть, тут нет).
- `movePath`: если не удалось удалить бэкап (`:510`), перенос уже сделан, а инструмент возвращает ошибку, и повтор падает с ENOENT. Проверка `destinationExists` (`:486`) и `rename` не атомарны, а `rename` на Windows молча заменяет существующий файл.
- `server-manager.ts:252`: `.env` сохраняется перезаписью, без temp + rename; сбой посередине записи оставит сервер без ключа и он не стартует.

## Что в порядке

- `ServerManager.start()` сделан single-flight через общий `startTask`, `stop()` переживает повтор и добивает процесс через 3 с; `before-quit` держит выход, пока сервер не отпустит порт; серверный `gracefulShutdown` идемпотентен и сам выходит через 3 с.
- Счётчики generation в `cli.ts` и `ngrok.ts` отбрасывают колбэки старых запусков; reconnect ngrok с экспоненциальной задержкой до 60 с.
- Память ограничена: логи в UI ≤ 1000, recent clients ≤ 50, console-логи браузера ≤ 100, SSE-сессий ≤ 32.
- `.env` создаётся с флагом `wx`, повторная инициализация безопасна; ошибки инструментов возвращаются как `isError`, а не роняют процесс.

## Что не проверял

- Headless-сценарий (п. 5), ReDoS и разрыв строк лога проверены только по коду.
- Нагрузку не мерил (McpServer и 24 инструмента создаются на каждый запрос к `/mcp`).
- Tuna и localtunnel на настоящих CLI; причину сбоев ngrok и перезапуска сервера в 13:31.

## Как воспроизвести

```
npm run build:server
node docs/audit/race-audit.cjs . A,B,C,D,G,I   # ~16 с
node docs/audit/race-audit.cjs . E             # ~50 с
```

Стенд поднимает отдельные экземпляры сервера на случайных портах localhost, песочница во временной папке, туннель фейковый; после себя всё удаляет. Рабочий сервер и его `.env` не трогает.
