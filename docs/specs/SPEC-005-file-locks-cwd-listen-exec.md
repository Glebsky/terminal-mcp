# SPEC-005 · Надёжность файловых инструментов, рабочей папки, запуска и terminal_execute

- **Статус:** Реализовано (ожидает ручной проверки в собранном приложении, T8)
- **Дата:** 2026-11-20
- **Область:** сервер (`src/`), десктоп (`desktop/src/main/server-manager.ts`)
- **Связано:** `docs/audit/2026-11-20-stability-races.md`, пункты 1–4 и `file_read` из «Средних»

## 1. Контекст и проблема

Аудит показал на стенде:

1. Из 20 параллельных `file_replace` одного файла «успех» возвращают 18–19, в файле остаются 2: read → modify → write без блокировки, перезапись поверх живого файла.
2. Рабочая папка одна на процесс: `workspace_set_cwd` одного агента уводит записи другого в чужой проект; относительный путь, которого нет в cwd, молча пишется в FILES_ROOT.
3. При занятом порте сервер шлёт `server:ready`: Express 5 передаёт ошибку в колбэк `listen`, а колбэк её игнорирует.
4. `terminal_execute` ждёт `close`, который держит любой фоновый процесс с унаследованным пайпом (`start /b ping` с таймаутом 1.5 с вернулся через 8.2 с); отмена запроса не останавливает команду.
5. `file_read` режет UTF-8 на границе куска: «привет» по 3 байта даёт `"п�"` + `"�и"`, чтение `ru.ts` с `length: 2000` кончилось на «Запустит�». Агент, который собирает файл по кускам и пишет обратно, портит кириллицу.

## 2. Требования

### FR-1 · Файлы
- FR-1.1 `file_write`, `file_replace`, `file_move`, `file_delete` на одном пути выполняются по очереди (FIFO-блокировка по нормализованному пути, на Windows без учёта регистра); `file_move` блокирует оба пути.
- FR-1.2 Перезапись (`file_write` без append, `file_replace`) атомарна: temp-файл в той же папке + `rename` с ретраями на EPERM / EBUSY / EACCES. Если `rename` так и не удался (файл держит другая программа), запись идёт на место под той же блокировкой.
- FR-1.3 `file_replace` отказывается от файла, который не декодируется в UTF-8 без потерь (cp1251 и т. п.).
- FR-1.4 Повтор `file_replace`: если target не найден, а непустой replacement встречается ровно один раз (и `allow_multiple=false`), ответ `replacements: 0, already_applied: true` без ошибки.
- FR-1.5 `file_move` не возвращает ошибку, если перенос прошёл, а удалить бэкап старого назначения не вышло: в ответе `backup_left`.

### FR-2 · Рабочая папка
- FR-2.1 Изменяющие операции (`file_write`, `file_replace`, `file_move`, `file_delete`, `file_mkdir`, путь `browser_screenshot`) резолвят относительный путь только от рабочей папки, без фолбэка в FILES_ROOT. Чтение, поиск, `workspace_set_cwd` и `cwd` у `terminal_execute` фолбэк сохраняют (на нём держится `workspace_set_cwd("имя_проекта")`).
- FR-2.2 У каждой SSE-сессии своя рабочая папка; она стартует с текущей общей на момент подключения. `workspace_set_cwd`, голый `cd` в `terminal_execute` и сброс после `file_delete` меняют только её.
- FR-2.3 `/mcp` без сессий продолжает работать с общей рабочей папкой процесса: каждый запрос там идёт в новый McpServer, и иначе `workspace_set_cwd` терялся бы между запросами.

### FR-3 · Запуск
- FR-3.1 Ошибка `listen` (EADDRINUSE, EACCES и др.) логируется, уходит по IPC как `server:error`, процесс выходит с кодом 1; `server:ready` не отправляется, туннель не запускается.
- FR-3.2 Десктоп показывает состояние error: «Port N is already in use by another process» для EADDRINUSE, иначе код и текст ошибки (тексты ошибок сервера и сейчас английские, SPEC-001).

### FR-4 · terminal_execute
- FR-4.1 Вызов возвращается не позже чем через `timeout + 2 с`, даже если фоновый процесс держит вывод.
- FR-4.2 После выхода оболочки вывод дочитывается не дольше 1 с; если пайпы всё ещё держит кто-то другой, результат возвращается с `backgroundLeft: true`.
- FR-4.3 Отмена запроса (клиент отключился или прислал `notifications/cancelled`) убивает дерево процессов, результат с `aborted: true`. MCP SDK 1.30 сам отменяет `extra.signal` при закрытии транспорта, достаточно его прокинуть.

### FR-5 · file_read по кускам
- FR-5.1 При `encoding=utf8` кусок не кончается посреди символа: конец сдвигается назад к границе последнего целого символа. Если от куска ничего не остаётся (`length` меньше одного символа), он расширяется до конца этого символа, чтобы чтение не зациклилось.
- FR-5.2 `offset` внутри многобайтового символа сдвигается назад к его началу (не больше 3 байт); в ответе `offset` фактический.
- FR-5.3 `bytes_read` равен фактически отданным байтам; пока файл не дочитан (`truncated: true`), в ответе есть `next_offset` (= `offset + bytes_read`), с которого читать дальше.
- FR-5.4 `encoding=base64` не меняется, байты отдаются как есть. Для файлов не в UTF-8 (cp1251) границы сдвигаются не больше чем на 3 байта, текст как и раньше декодируется с потерями: такие файлы читаются через base64.

### Не входит в задачу
- Stateful Streamable HTTP (`Mcp-Session-Id`) для `/mcp`: клиенты `/mcp` делят рабочую папку как раньше.
- Убийство осиротевших фоновых процессов (нужен Job Object): о них только сообщается.
- Пункты 5–6 аудита и остальные средние/мелкие, кроме FR-1.3, FR-1.5 и FR-5.

## 3. Дизайн

- `src/tools/filesystem.ts`: `withPathLock(paths, fn)` (очередь промисов на ключ; все ключи берутся синхронно в одном тике, поэтому взаимных блокировок нет), `atomicWrite`, `renameWithRetry`; `resolveTarget(input, { cwd, mutating })`; `WorkspaceScope { get, set }`, `globalScope`, `createSessionScope()`. Чтения блокировку не берут: при атомарной записи они видят старую или новую версию целиком.
- `src/tools/index.ts`: `registerAllTools(server, scope)`; файловые инструменты получают `scope.get()`, `terminal_execute` получает `scope` и `extra.signal`.
- `src/server.ts`: `/mcp` → `globalScope`, `/sse` → `createSessionScope()`.
- `src/tools/command.ts`: завершение по `close`, по `exit` + 1 с или по потолку `timeout + 2 с`, что наступит раньше; потом `stdout/stderr.destroy()`.
- `src/index.ts`: колбэк `listen(err)`; `desktop/src/main/server-manager.ts`: сообщение `server:error`.
- `readFile` (`src/tools/filesystem.ts`): для utf8 дочитывает до 3 байт перед `offset` и после конца куска, обе границы выравнивает по lead-байту (не `10xxxxxx`), длину символа берёт из lead-байта (`110` / `1110` / `11110`).
- Ограничения: атомарный `rename` разрывает жёсткие ссылки и заменяет явные ACL файла наследуемыми; блокировка действует внутри одного сервера, другие программы её не видят.
