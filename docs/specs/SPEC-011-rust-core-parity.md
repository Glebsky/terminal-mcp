# SPEC-011 · Rust-ядро рядом с действующим TS-сервером

Статус: в работе. R1 проверен локально на Windows. Реализация по частям, без переключения рабочего MCP. База: `bb0816e` (SPEC-009 + SPEC-010). Стек Rust и последующий Tauri 2 выбраны владельцем; Tauri не входит в эту спецификацию. [Архитектурное решение](../audit/2026-11-28-zeroide-parity.md), [контракт инструментов](../../contracts/tools.json), [протокол десктопа](../../contracts/control.md).

## Что должно измениться

После полной миграции клиент и текущий Electron должны работать с нативным сервером так же, как с TypeScript. Префикс `notion-terminal-files`, имена инструментов, четыре аннотации, входные схемы, форма текстовых результатов и правила SPEC-005/006/009/010 остаются контрактом. Старый сервер остаётся эталоном и вариантом запуска по умолчанию до отдельного решения владельца. Не выдавать схему из каталога за реализованную операцию.

## Первый срез: локальный процесс, один настоящий инструмент

- Отдельный бинарник `mcp-terminal-server`. Rust-код предметной логики в `crates/core`; процесс и транспорт в `crates/server`. Cargo workspace и lock-файл в корне. Никакой подмены `dist/index.js`, изменений установщика или запускающего процесса Electron.
- `GET /health` выдаёт `{status:"ok",server:"notion-terminal-files",version:<версия приложения>}` после фактического bind. Родительский канал SPEC-009 это **не** MCP-stdio: готовность и отключённый туннель идут в stdout как `[CTL] ` + JSON; `shutdown` и EOF на stdin завершают процесс; занятый порт даёт `server:error/EADDRINUSE`, код выхода 1, без ложного ready. Полные счётчики монитора относятся к следующему этапу, никаких нарисованных снимков.
- Только явно запущенная тестовая копия: IPv4 loopback, явные свободный `PORT`, существующий абсолютный `FILES_ROOT`, новый тестовый `MCP_API_KEY` длиной не менее 32 и `MCP_CONTROL=stdio`. Токен в заголовке Bearer либо `X-API-Key`; неподходящий Host отклоняется до handler. Не читать рабочий `.env`, не открывать внешний интерфейс, не запускать провайдеров, не принимать `FULL_ACCESS=true` или неподдержанную схему авторизации. Пользователю не нужен компилятор для будущего готового бинарника.
- `POST /mcp` обслуживает официальный Rust SDK `rmcp` и axum. Клиент версии `2025-11-25` проходит `initialize`. Для `2026-07-28` нет рукопожатия: версия и данные клиента передаются в каждом запросе; проверять отдельно `server/discover` и вызов без `initialize`. Это две проверки, а не гарантия всей ревизии. Ссылка: [новый lifecycle](https://modelcontextprotocol.io/specification/2026-07-28/basic/lifecycle), [старый lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [rmcp](https://github.com/modelcontextprotocol/rust-sdk/releases/tag/rmcp-v3.12.0).
- Первый работающий вызов `workspace_get_cwd({})`: один блок `content` типа `text`; в нём JSON с полями `cwd` и `files_root`, оба указывают на тестовую рабочую папку. `tools/list` возвращает только этот инструмент с тем же описанием, схемой и аннотациями, что у TS. Если имя есть в `DISABLED_TOOLS`, инструмент не перечисляется и не вызывается. Остальные 23 пока не заявляются. Нет чтения пользовательских файлов, модификаций, дочерних процессов, браузера или туннелей из инструментов первого среза.

Включение Rust по умолчанию, релиз и слияние с `master` требуют отдельного решения.

### Открытая граница до `workspace_set_cwd`

У текущего TS обычный `/mcp` использует общую рабочую директорию, legacy SSE создаёт локальный scope. Новая ревизия не даёт legacy session id. Отображаемое имя в `clientInfo` не является идентификатором для разграничения доступа. До реализации изменяемого cwd выбрать и проверить семантику для двух независимых клиентов; не менять поведение молча. Первый срез рабочую папку не меняет и не требует этого решения. Открытые пункты приёмки SPEC-010 также не считаются закрытыми переносом.

### Как повторить первый срез

На Windows с x64 MSVC, Rust и Node 24: `npm ci --omit=dev --ignore-scripts` устанавливает только существующие runtime-зависимости для JS-клиента тестов. Затем `cargo fmt --all -- --check`, `cargo build --workspace --locked`, `cargo test --workspace --locked` и `node --test tests/rust/bootstrap.test.mjs`. Проверяемая версия компилятора: Rust 1.100.1 для `x86_64-pc-windows-msvc`. У процесса сервера нет зависимости от Node; Node нужен сквозному тесту. Если `CARGO_TARGET_DIR` вынесен на другой диск, указать `RUST_MCP_BIN` с абсолютным путём к собранному debug-бинарнику. Установленный TS-сервер для этих тестов не нужен. Полный тестовый набор SPEC-009 должен продолжать требовать 24 инструмента.
## Граница совместимости первого этапа

| Действие | Реализовано в R1 | Остаётся до переключения продукта |
|---|---|---|
| Получить доступные инструменты | Только `workspace_get_cwd` (или пусто, если выключен); точное совпадение дескриптора со снимком TS | Реальные обработчики оставшихся 23, а не список обещаний |
| Подключить клиент | Streamable HTTP: legacy `initialize`, modern прямой `tools/call` и `server/discover`; штатный клиент `@modelcontextprotocol/sdk` по lock-файлу | Старый HTTP+SSE и остальные совместимые клиенты. Принятие `2025-11-25` само по себе не доказывает поддержку всех старых ревизий |
| Запустить и остановить | Дочерний процесс с приватными каналами: `[CTL] server:ready`, `server:error`, отсутствие туннеля, `shutdown`/EOF | Приёмка с настоящим Electron и данными монитора; сейчас Electron по-прежнему запускает только TS |
| Защита | Только loopback, явный корень, проверка Host/Origin, ключ в заголовке, скрытие выключенного инструмента; нет чтения или записи файлов, запуска команд или браузера | Сохранение всех гарантий SPEC-010, ограничений частоты и конфигурации по мере добавления новых возможностей. Это не замена выпущенного сервера |

Для Windows подготовлена отдельная проверка `.github/workflows/rust-core.yml`; она не заменяет текущую TS CI. Сама запись workflow не является результатом запуска в GitHub.
## Что проверено 28.11.2026

- Из реальных исходников собран Windows x64 `mcp-terminal-server.exe`: Rust/Cargo 1.100.1 (MSVC), официальный `rmcp` 3.12.0, axum 0.8.9. Использован отдельный toolchain; системные Rust, PATH и программа владельца не изменялись.
- Пустой скомпилированный процесс сначала провалил 5 сценариев по ожидаемой причине (нет ready/ошибки старта). После реализации `cargo fmt --check`, `cargo build --locked --workspace` и 3 модульных теста прошли. Финальный чёрный ящик: 7 из 7 без пропусков. Использовался именно Rust executable, а не TS как запасной сервер; адрес, ключ и тестовая папка создавались заново.
- Проверены первый современный вызов без discover/initialize, затем discover; отдельный legacy initialize; отказ с кодом `-32022` и перечнем версий для неизвестной ревизии. Существующий JS SDK 1.30.0 из lock-файла отдельно подключился и получил реальный результат. Содержимое `contracts/tools.json` не менялось.
- Сначала обнаружено расхождение с TS при завершающем `.`/разделителе в `FILES_ROOT`; регрессия исправлена. Проверка с двумя именами одного временного каталога подтверждает, что клиент получает нормализованный путь, но не теряет имя, выбранное владельцем. Проверены занятый порт, EOF, фрагментированный shutdown и повторное занятие освободившегося порта. Публичного адреса, подключённого профиля браузера и настоящих ключей в проверках нет.
- **Следующий проверяемый результат (R2):** тест действующего Electron manager должен получить от отдельного Rust-процесса настоящий `monitor:snapshot` после авторизованного локального запроса, перестать получать его после `monitor:set=false` и корректно завершить процесс. Для legacy `/sse` отдельный тест ожидает `endpoint`, затем ответ на `POST /messages` по сессии. Текущий R1 не доказывает ни один из этих пунктов.
- В той же рабочей копии повторно прошли проверка типов и сборка исходного TS-приложения, 19/19 его conformance-тестов (с браузером), 3/3 проверки desktop-control и тест монитора. Эти результаты относятся к TS-эталону, **не** к полному паритету Rust. Обе серии запускали только собственные временные процессы.
